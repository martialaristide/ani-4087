Ce qui change : la table, et elle seule. Dans correspondance.cpp, c'est ce que lit la fonction jouerTable dans la structure table (usage vers commande). Elle est donnée ici en entrée : les lignes SELECT SOURIS_G ou SELECT ESPACE du fichier d'entrée. Sur un vrai casque, ce morceau serait remplacé par les liaisons du casque : la même ligne usage, commande, avec les commandes de ses manettes à la place de la souris ou du clavier. Le reste ne bouge pas : la liste des actions (nom et usage), la détection de l'appui, le journal des images et la comparaison.

Aucun nom de bouton : dans le code, la seule chose qui relie une action à une commande est table.find(a.usage), puis tenues.count(it->second). Les noms de commande (SOURIS_G, SOURIS_D, TAB, ESPACE, E) ne sont jamais écrits dans le code : ils viennent de l'entrée, et le programme ne fait que les comparer. J'ai vérifié avec grep -w sur ces noms et sur les usages (SELECT, GRAB, MENU) : aucune ligne du code ne les contient. Passer de la première table à la seconde, c'est donc changer des données, pas du code : les deux tables rendent les mêmes lignes d'images, et la sortie finale dit IDENTIQUES OUI.

L'action inactive : saisir_g a l'usage GRAB_LEFT, et ni la première ni la seconde table n'a de ligne GRAB_LEFT. Le programme l'écrit donc INACTIVE saisir_g dans les deux tables. Une action inactive n'est jamais appuyée : elle ne figure sur aucune ligne d'image, et rien d'autre ne le signale que ce journal INACTIVE. Sur un vrai casque, d'après le cours, une action sans liaison se lit comme relâchée, sans erreur ni message : elle rendrait toujours « rien », comme ici. C'est pour cela qu'il faut écrire le journal soi-même.
